# תוכנית פעולה — שלבי בנייה עם Claude Code

עקרון מנחה: **כל שלב נבנה על בסיס יציב ונבדק של השלב הקודם**. לא עוברים לשלב הבא לפני שסעיף ה"הגדרת סיום" (Definition of Done) של השלב הנוכחי מסומן כ-✅ ונדחף ל-`main` בפועל. הפירוט המלא של המוצר ב-`product-spec.md`, הפירוט הטכני ב-`architecture.md`.

לכל שלב מצורף **טקסט קיקאוף מוכן** — זה בדיוק מה שמעתיקים להודעה הראשונה לקלוד קוד כדי לפתוח את השלב. קלוד קוד תמיד יקרא קודם את `CLAUDE.md`, ולפי ההנחיה שם גם את שלושת המסמכים בתיקיית `docs/`.

---

## Phase 0 — תשתית ובסיס פרויקט

**מטרה:** ריפו עובד, ריק מבחינת פיצ'רים, אבל עם כל התשתית שכל שלב עתידי יישען עליה — כדי שקלוד קוד לא "יתחיל מאפס" בכל שיחה.

**מה נכלל:**
- יצירת ריפו ב-GitHub (פרטי), חיבור ל-Vercel.
- יצירת פרויקט Supabase, חיבור מקומי (`supabase` CLI), הפעלת extension ל-PostGIS.
- Scaffold של Next.js (App Router, TypeScript strict, Tailwind), מבנה התיקיות מ-`architecture.md` סעיף 2.
- הטמעת `CLAUDE.md` ותיקיית `docs/` (המסמכים האלה) בשורש הריפו.
- `.env.example` עם כל המשתנים הנדרשים (ריק מסודות אמיתיים).
- ESLint + Prettier + husky pre-commit (lint על כל commit).
- `README.md` בסיסי: איך מריצים מקומית.
- דף בית זמני ("Hello Handy") שמוכיח שה-build עובד ושה-deploy ל-Vercel מצליח.

**הגדרת סיום:**
- [x] `npm run build` ו-`npm run lint` עוברים (וגם `npm run typecheck` ו-`format:check`)
- [ ] דיפלוי ל-Vercel חי ונגיש — **ממתין למשתמש**: הקוד וה-CI מוכנים, החיבור בדשבורד Vercel נעשה על ידיו
- [x] פרויקט Supabase מחובר, ניתן להריץ `supabase migration list` בהצלחה — עובד מול הסטאק הלוקאלי (`--local`); הלינק לפרויקט הקלאוד (`supabase login` + `link`) **ממתין למשתמש** כי הוא דורש טוקן אישי
- [x] `CLAUDE.md` ו-`docs/*.md` נמצאים בריפו
- [x] commit ראשון ב-`main`, לפי מוסכמת ה-commits מ-`CLAUDE.md`

**הערה:** Vitest לא הוקם ב-Phase 0 — הוא לא מופיע ברשימת "מה נכלל" של השלב, וכלל "שלב אחד בכל פעם" אוסר לבנות קדימה. יוקם בשלב שידרוש אותו בפועל.

**טקסט קיקאוף לקלוד קוד:**
> קרא את `CLAUDE.md` ואת כל הקבצים ב-`docs/`. נתחיל ב-Phase 0 מתוך `docs/roadmap.md`: הקמת תשתית הפרויקט בלבד — Next.js scaffold, חיבור Supabase, מבנה תיקיות, lint/CI בסיסי, ודף בית זמני שמוכיח שהכל עובד. אל תבנה שום פיצ'ר מוצרי בשלב הזה. בסוף, ודא שכל סעיפי ה"הגדרת סיום" של Phase 0 מתקיימים, ותן לי סיכום.

## Phase 1 — מסד נתונים + אימות (הבסיס האמיתי)

**מטרה:** כל סכימת ה-DB מ-`architecture.md` קיימת כ-migrations אמיתיים עם RLS, וזרימת ההתחברות (טלפון+OTP) עובדת מקצה לקצה לשני התפקידים.

**מה נכלל:**
- Migrations לכל הטבלאות בסעיף 3 של `architecture.md` (`profiles`, `pro_profiles`, `verification_documents`, `categories`, `jobs`, `bids`, `price_updates`, `messages`, `reviews`, `commission_charges`, `disputes`, `saved_pros`).
- מדיניות RLS לכל טבלה (לפי סעיף 4 של `architecture.md`).
- הגדרת Supabase Auth Phone Provider + Twilio.
- מסכי כניסה (טלפון → OTP) ללקוח ולבעל מקצוע, כולל יצירת שורת `profiles` אוטומטית עם `role` נכון.
- Middleware/הפניה לפי role (לקוח → `/(customer)`, בעל מקצוע → `/(pro)`, אדמין → `/(admin)`).
- `seed.sql` עם כמה קטגוריות (`categories`) ומשתמשי דמו.

**הגדרת סיום:**
- [x] כל הטבלאות קיימות עם RLS, ונבדק ידנית: לקוח א׳ לא יכול לראות קריאה של לקוח ב׳ — נבדק גם דרך PostgREST עם JWT אמיתי וגם ב-33 בדיקות pgTAP (`npm run db:test`)
- [ ] אפשר להתחבר בפועל עם מספר טלפון אמיתי ולקבל SMS — **ממתין למשתמש**: הזרימה בנויה ועובדת מקצה לקצה מול `[auth.sms.test_otp]`; SMS אמיתי דורש חשבון Twilio ופרויקט Supabase Cloud מקושר (ראו README, "Going live with Twilio")
- [x] קיים מסך "מי אני" בסיסי שמראה role + פרטי המשתמש שהתחבר — `/account`, `/pro`, `/admin`
- [x] `docs/architecture.md` מעודכן אם היו סטיות מהטיוטה המקורית — ראו "סטיות מהטיוטה" ו"מבנה נתיבים ותפקידים" בסעיף 3

**החלטות שנפלו בשלב הזה** (הפירוט ב-`docs/architecture.md` סעיף 3):
- מבנה נתיבים: לקוח בשורש (`/login`, `/account`), בעל מקצוע ואדמין עם prefix.
- הרשאות ברמת עמודה בנוסף ל-RLS — זה מה שמונע מלקוח להגדיר את עצמו `admin` ומבעל מקצוע לאמת את עצמו.
- `proxy.ts` (השם החדש של `middleware.ts` ב-Next 16) עושה רק רענון סשן ושער אנונימי; אכיפת role ב-layout.
- בדיקות RLS כ-pgTAP, לא Vitest — אין לוגיקה שמצדיקה Vitest בשלב הזה.

**טקסט קיקאוף לקלוד קוד:**
> ננוע ל-Phase 1 מתוך `docs/roadmap.md`: הקמת מסד הנתונים המלא לפי `docs/architecture.md` סעיף 3 (migrations לכל הטבלאות, כולל RLS לפי סעיף 4), והקמת אימות טלפון+OTP דרך Supabase Auth ל-2 התפקידים (לקוח, בעל מקצוע). אל תבנה עדיין את מסכי המוצר עצמם (פרסום קריאה וכו') — רק את השכבה הזו. בסוף, הרץ בדיקת RLS ידנית (נסה לגשת לנתונים של משתמש אחר) ודווח.
