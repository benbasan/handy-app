# איך לעבוד עם Claude Code על הפרויקט הזה

זה המסמך שעונה ישירות על השאלה "איך נכון לעבוד עם קלוד קוד": סדר פעולות, מה לבקש ממנו, ואיך לוודא שהוא בונה תשתית טובה, לא ממציא את הגלגל מחדש, ודוחף לגיט בצורה מסודרת.

## 1. הקמה ראשונית (חד-פעמי)

1. צרו ריפו חדש ב-GitHub (פרטי, בשם למשל `handy-app`).
2. שימו בשורש הריפו את `CLAUDE.md` ואת תיקיית `docs/` (4 הקבצים האלה) — **לפני** שמריצים את Claude Code בכלל. הוא קורא את `CLAUDE.md` אוטומטית בתחילת כל שיחה בריפו הזה, וזה מה שנותן לו "זיכרון" של ההחלטות בין שיחות.
3. פתחו את Claude Code בתוך תיקיית הריפו המקומית (`cd handy-app && claude`).
4. ההודעה הראשונה שלכם צריכה להיות פשוט:
   > קרא את CLAUDE.md ואת כל הקבצים ב-docs/, ותסכם לי בקצרה מה הבנת על הפרויקט לפני שנתחיל.
   
   זה מוודא שהוא באמת קרא הכל לפני שמתחילים לעבוד, ונותן לכם הזדמנות לתקן טעויות הבנה מוקדם.
5. משם תמשיכו לפי `roadmap.md` — כל שלב יש לו "טקסט קיקאוף" מוכן להעתקה.

## 2. הכלל הכי חשוב: שלב אחד בכל פעם

אל תבקשו "תבנה לי את כל האתר". גם אם תנסחו את זה יפה, זה יגרום לו לקצר פינות, לדלג על RLS, ולערבב שכבות. **תמיד** תכוונו אותו לשלב ספציפי מתוך `roadmap.md`, ורק אחרי שסעיפי ה"הגדרת סיום" של השלב מתקיימים בפועל — עוברים הלאה.

טיפ מעשי: תתחילו כל שיחה חדשה (session) עם "אנחנו ב-Phase X, לפי docs/roadmap.md" — גם אם דיברתם על זה בשיחה קודמת. Claude Code לא זוכר שיחות קודמות אלא אם הן באותו session, וקבצי הפרויקט (CLAUDE.md + docs) הם הדרך שלכם לתת לו "זיכרון" עקבי.

## 3. איך למנוע ממנו "להמציא את הגלגל מחדש"

זו בדיוק הסיבה ש-`CLAUDE.md` קיים. שלושה כללים:

- **אל תיתנו לו להחליט טכנולוגיה תוך כדי עבודה.** אם הוא מציע ספרייה/גישה שלא מופיעה ב-`CLAUDE.md`, תעצרו אותו: "זה לא ההחלטה שרשומה ב-CLAUDE.md — תסביר למה אתה מציע לסטות, ואם אני מסכים נעדכן את המסמך יחד". ההחלטות הטכנולוגיות כבר נעולות במסמך (Next.js, Supabase, Google Maps, Twilio) בדיוק כדי שלא תתקבלנה שוב ושוב בכל שיחה.
- **כל החלטה חדשה נכתבת מיד לתוך המסמכים.** אם במהלך עבודה מתקבלת החלטה (למשל: איזו ספריית PDF לקבלות), תבקשו ממנו במפורש: "עדכן את CLAUDE.md/architecture.md עם ההחלטה הזו לפני שאתה ממשיך לממש". סעיף 9 ב-`CLAUDE.md` ("החלטות פתוחות") נבנה בדיוק בשביל זה.
- **שינויי סכימה תמיד דרך migration.** אל תאשרו לו "אני אעדכן ידנית בממשק של Supabase, זה יותר מהיר" — זה בדיוק מה שגורם לו לאבד את התמונה האמיתית של ה-DB בשיחה הבאה. ב-`CLAUDE.md` זה כבר כתוב ככלל ברזל.

## 4. איך לבדוק את העבודה שלו לפני שמאשרים

לפני שמאשרים merge של כל שלב:

1. תבקשו ממנו לעבור בעצמו על רשימת ה"הגדרת סיום" של השלב (ב-`roadmap.md`) ולסמן מה עבר ומה לא.
2. תסתכלו בעצמכם על ה-diff (`git diff` / תצוגת הפייל צ'יינג'ז) — גם אם אתם לא מתכנתים מנוסים, תבדקו שהוא לא הוסיף קבצים מוזרים, לא חשף מפתחות API, ולא "דילג" על RLS.
3. תריצו את האתר בעצמכם (מקומית או ב-Vercel preview) ותעברו על הזרימה שהשלב מכסה — לא רק "זה נראה שזה עובד" אלא לחיצה בפועל על הכפתורים.
4. רק אז תבקשו ממנו לפתוח Pull Request ל-`main` (או למזג ישירות אם אתם עובדים לבד ונוח לכם ככה — אבל PR נותן לכם "עצירה" נוחה לבדוק לפני שהקוד נכנס ל-main).

## 5. גיט — איך זה אמור להיראות בפועל

לפי `CLAUDE.md` סעיף 6: branch לכל שלב, commits קטנים בתוך ה-branch, Conventional Commits, PR למיזוג. בפועל, ההודעה שלכם יכולה להיות:

> תתחיל branch חדש בשם phase-2-customer-job-flow, תעבוד עליו, ותעשה commit נפרד לכל חלק לוגי (לא הכל בסוף בcommit אחד).

ובסיום שלב:

> נראה לי ש-Phase 2 מוכן. תעבור על ה-Definition of Done ב-roadmap.md, תעדכן שם את הצ'קליסט, ותפתח PR ל-main עם תיאור של מה נבנה.

## 6. איך לנסח בקשות טוב יותר (טיפים כלליים)

- **תפנו למסמכים במפורש** ("לפי docs/product-spec.md סעיף 3.5") במקום לתאר שוב את הפיצ'ר במילים שלכם — זה מונע אי-התאמות בין מה שאתם מתארים למה שכבר כתוב.
- **תבקשו הסבר לפני שינוי גדול**: "לפני שאתה מממש, תסביר לי בקצרה את הגישה שאתה מתכנן" — נותן לכם הזדמנות לתפוס בעיה לפני שנכתב קוד.
- **תבקשו טסטים לזרימות קריטיות**, במיוחד Phase 5 (עדכון מחיר) — זה החוק העסקי שהכי חשוב שלא יישבר בטעות בעתיד.
- **כשמשהו לא עובד**, תנו לו את הודעת השגיאה המדויקת ואת מה שכבר ניסיתם — לא רק "זה לא עובד".
- אם יש ל-Claude Code אצלכם "Plan Mode" — כדאי להשתמש בו לשלבים גדולים/מורכבים (למשל Phase 1 או Phase 5): הוא יציג תוכנית מפורטת לפני שהוא נוגע בקוד, ואתם מאשרים או מתקנים לפני ביצוע.

## 7. ריצה אוטונומית של כמה שלבים ברצף

`run-all-phases.sh` בשורש הריפו בונה שלבים ברצף בלי שתאשר כל אחד. הוא מריץ
**תהליך Claude Code נפרד לכל שלב** — session נקי לגמרי, בלי היסטוריה מהשלב
הקודם, בדיוק כמו שסעיף 2 ממליץ לעשות ידנית. הפרומט שכל שלב מקבל נמצא
ב-`docs/autonomous-run-prompt.md` וניתן לעריכה שם (הסקריפט לא צריך שינוי).

מה שמחזיק את האיכות זה לא ההצהרה של הסוכן שסיים, אלא **שער איכות שהסקריפט
מריץ בעצמו** לפני כל מיזוג: `lint`, `typecheck`, `build`, `db:reset`, `db:test`,
עץ עבודה נקי, יש commits, אין סוד שדלף ל-diff, ובדיקת RTL על utilities פיזיים.
נכשל → סוכן תיקון מקבל את לוג הכישלון ומנסה שוב (עד 2 פעמים); עדיין נכשל → כל
הריצה נעצרת, `main` נשאר נקי, וה-branch נשאר לבדיקה.

```bash
./run-all-phases.sh --preflight      # בדיקות סביבה בלבד
DRY_RUN=1 ./run-all-phases.sh        # מדפיס את הפרומטים ואת התוכנית, לא מריץ כלום
PHASES="2" ./run-all-phases.sh       # שלב אחד, מקצה לקצה
mkdir -p .runner-logs && nohup ./run-all-phases.sh > .runner-logs/run.log 2>&1 &   # הריצה המלאה
tail -f .runner-logs/run.log         # מעקב
```

**מה זה עדיין לא מחליף:** השער מוכיח שהקוד תקין, לא שהמוצר טוב. התאמה לצילומי
המסך ב-`design/screens/`, מעבר בפועל על הזרימות בדפדפן, וכל סעיף שסומן "ממתין
למשתמש" (Twilio, Vercel) — נשארים עליך, בסוף הריצה. לשלבים שבהם אתה רוצה לשבת
עם קלוד קוד ולכוון תוך כדי (למשל Phase 5), עדיף עבודה ידנית עם הקיקאוף
מ-`roadmap.md` מאשר הריצה האוטונומית.

## 8. תחזוקת המסמכים — זה לא "כתוב פעם אחת ונשכח"

- כל פעם שמתקבלת החלטה טכנית חדשה → מתעדכן `CLAUDE.md`.
- כל פעם שמתגלה שהמציאות בשטח שונה מהתכנון (למשל: טבלה נוספת שהתגלה שצריך) → מתעדכן `architecture.md`.
- כל פעם ששלב מסתיים → מתעדכן הצ'קליסט ב-`roadmap.md`.
- אם יש שינוי אמיתי בהיקף המוצר (לא רק טכני) → מתעדכן `product-spec.md`, ורצוי שהשינוי הזה יעבור קודם דרככם (המשתמש), לא רק דרך קלוד קוד.

מסמכים שלא מתעדכנים הופכים תוך כמה שבועות ל"שקר" שגורם לקלוד קוד לקבל החלטות לפי מידע ישן — זה בדיוק המצב שרציתם למנוע.
